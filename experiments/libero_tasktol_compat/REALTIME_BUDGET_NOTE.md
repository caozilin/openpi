# 原始20Hz与默认IPOPT 95ms预算

`IpoptSettings.max_cpu_time_s=0.095`被原样传给IPOPT的`max_cpu_time`。这是求解CPU时间上限，不是每次固定95ms，更不是整条客户端链路的硬墙钟截止时间。适配器`elapsed_ms`由`perf_counter`测量`problem.solve(seed)`的墙钟时间；前后参数构造、求解后验证、客户端处理及物理步进不在这个计时范围内。

当前离线录制顺序是“完成求解→原生LIBERO执行25个2ms物理步”，相邻动作保持50ms仿真时间。等待计算期间不推进仿真，所以数据20Hz与95ms上限不会直接造成离线物理时序冲突；其任务成功率和跟踪误差没有包含计算延迟效应。

2026-10-24，400条固定抽样批次已完成43条时，从115次实际录制提取12934次求解调用：中位数19.30ms、P95 26.64ms、P99 33.55ms、最大123.38ms；26次超过50ms，占0.201%。可行调用中19/12927次超过50ms，约0.147%。详细快照保存在`results/task_pose_default_ipopt400_v1/timing_snapshot.json`。这些来自6路并行、包含渲染的离线作业，不是隔离资源的部署时延基准；不能把它们直接作为稳定20Hz保证。

当前继续原速重录，默认优化器、原始时间格和夹爪不改。部署前需要单独测量目标运行环境下的完整客户端墙钟延迟及P95/P99、50ms deadline miss，并计入VLA动作消费、IPC和观测时延。即使平均求解小于50ms，尾部超时仍需要明确策略。

## 求解拒发与50ms截止时间超出是两类事件

超过50ms墙钟时间并不自动触发当前框架拒发：如果求解正常终止且通过非线性可行性验证，离线客户端仍发布完整关节参考，再执行25个物理步。例如Spatial00/demo_0首次baseline的第0帧，`elapsed_ms=114.7169`、正常最优终止、`feasible=true`、`physics_steps=25`。CPU时间上限与墙钟耗时不是同一计时。

真正的拒发由原控制器的发布判定决定：终止状态必须属于原有允许集合，且候选必须通过可行性验证。核对源码后的纠正：原允许集合为`{0,1,6,-1,-4}`，CPU超时`-4`和迭代上限`-1`在候选独立可行时仍允许发布，不能将CPU超时状态本身当作拒发原因。LIBERO重录客户端发现`diagnostics.feasible=false`后直接终止该示范，该帧`physics_steps=0`，没有把一次超时模拟成延迟后继续执行。

83条完成时，最终选择结果为72成功、11拒解；全部已运行候选合计13个拒解帧（含2个未被选中的修正候选），日志状态均为`ipopt: Maximum CPU time exceeded.`。例：Spatial00/demo_36 baseline第92帧，10次迭代、117.8281ms墙钟、拒发且0物理步。这只能证明默认预算内未取得可发布解，不能仅据该状态证明目标不可达、关节限位或奇异。

需要注意：拒发时控制器返回上次已发布关节指令，部分diagnostics残差也基于该保留指令对新目标计算。不能将轨迹JSON中的拒发残差直接当作IPOPT最后一次未发布迭代的残差来诊断不可达。

后续已完成27帧隔离复测、12个原拒解帧的原始候选复算和FK热点微基准，见`SLOW_IPOPT_FINDINGS_20261024.md`。主要额外耗时来自FK临时场景默认物体重叠后仍调用完整`mj_forward`，默认IPOPT、生产FK和400条抽样协议均未修改。

若实际总链路能稳定满足50ms预算，可以保持20Hz直接执行。如果不能，保持上一关节参考、异步求解或预瞄可以避免主控制循环阻塞，但不会让新解凭空以20Hz产出，也会带来动作陈旧和控制延迟。需要显式的时间戳/过期处理，以及与该延迟一致的重构仿真和部署验证。不能仅靠本次“求解时冻结仿真”的成功轨迹证明延迟闭环可用，也不应在未测量前把原数据减速或修改默认IPOPT。
